# Rebuild the DayZ Editor's techniques, not its code

The DayZ Editor is a client-side mod built around one very large `Editor` singleton. It runs on top of Community Framework and Dabs Framework. The DayZ Editor Loader is a separate, roughly 260-line `modded class MissionServer`. At mission start it reads `.dze` files from `$mission:\EditorFiles`, spawns their objects as ordinary networked entities, and hides deleted map objects on the server and on every client by "suppressing" them. Almost everything that makes the editor good to use comes down to a handful of portable ideas. Picking is a cursor ray built from `GetPointerDirection()`. Moving and rotating is plane intersection plus a ray-versus-box test on the gizmo handles. Box selection compares projected screen positions. Placement sits the object's lowest bounding-box point on the ray hit. Undo is a stack of before/after snapshots. All of this maps onto vanilla 1.30 Enforce APIs with no framework dependency. The hard constraint is legal. DayZ Editor and Dabs Framework (like Expansion) are CC BY-NC-ND 4.0 and carry explicit no-repack terms. Any of their code adapted into a PBO that ships to players is prohibited Adapted Material, so DRPA_Editor must be a clean-room reimplementation of the techniques, written from engine API documentation and the math, never from their source. Three behaviours decide the design and are not proven for retail DayZ 1.30, so they must be tested in game before we commit to them: whether `Shape` debug drawing renders in the retail client, whether static buildings moved after creation sync to clients, and which map-object removal method (`ObjectDelete`, suppression, or move-down) is safe and visible on every client. The recommended plan has five phases. It starts with a server-authoritative JSON editor set and a map-object hide pipeline. It adds picking, selection and undo next, then the gizmo, then the object browser, and ends with import/export compatibility with `.dze`, Expansion `.map` and the vanilla Object Spawner.

## One 3,700-line singleton sitting on two frameworks

The active code is the `legacy` branch, not `production` or `development`. Its last commit is a55ec49, dated 2026-10-25. The GitHub releases stop at v0.1.21 from 2020, so the Workshop is the real release channel ([DayZ-Editor repo](https://github.com/InclementDab/DayZ-Editor)). The mod has **302 script files and about 30k lines**, and nearly all of the logic sits in `4_World`. **`Editor.c` alone is 3,743 lines**. It owns the camera, the selection, the undo stack, the objects "in hand" for placement, and input. Around it sit an object-manager module, **about 100 command classes** (each carrying its own name, shortcut, `CanExecute` and `Execute`), gizmo entity classes, and drag handlers ([Editor.c](https://github.com/InclementDab/DayZ-Editor/blob/legacy/DayZEditor/Scripts/4_World/DayZEditor/classes/Editor.c)). `config.cpp` lists `JM_CF_Scripts` and `DF_Scripts` as required addons and replaces the mission script module with its own `CreateEditorMission` ([config.cpp](https://github.com/InclementDab/DayZ-Editor/blob/legacy/DayZEditor/Scripts/config.cpp)).

The dependencies are lopsided. Community Framework appears mostly in config. In code it shows up only where the editor suppresses COT input actions. No `CF_`/`JM_` types turned up in the gizmo, drag or selection code that was searched, but a full-repo audit was not done. Dabs Framework, by contrast, supplies several core pieces. It provides the `Ray`/`Raycast` wrappers over `DayZPhysics.RayCastBullet` and `RaycastRVProxy` ([DF Ray.c](https://github.com/InclementDab/DayZ-Dabs-Framework/blob/production/DabsFramework/Scripts/3_Game/DabsFramework/!Core/Ray.c)). It provides the `SuppressedObjectManager` that hides map objects ([DF Suppression](https://github.com/InclementDab/DayZ-Dabs-Framework/tree/production/DabsFramework/Scripts/3_Game/DabsFramework/Suppression)). It holds the save-data classes (`EditorSaveData`, `EditorObjectData`, `EditorDeletedObjectData`), and the MVC UI layer (`ScriptView`, `ObservableCollection`). So "no CF, no DF" means we replace the ray helpers, the suppression system, the file schema and the UI binding. None of these is large, and none of the gizmo math depends on either framework.

The Workshop page still calls the editor offline-only ([Workshop 2250764298](https://steamcommunity.com/sharedfiles/filedetails/?id=2250764298)). The current code nevertheless has multiplayer paths: `IsMultiplayer()` branches send ScriptRPCs for delete and hide, and `EditorNetActionManager` streams drag sessions, sending a network update every 30 frames during a gizmo drag ([GizmoBase.c](https://github.com/InclementDab/DayZ-Editor/blob/legacy/DayZEditor/Scripts/4_World/DayZEditor/objects/GizmoBase.c)). That work is recent and experimental. DRPA_Editor starts the other way round, server-authoritative by design, which is the correct choice for an admin tool on a live server.

## Picking, gizmos and marquee selection rest on three geometric ideas

### Every frame starts with one cached cursor ray

Each frame the editor builds a ray from `GetCurrentCameraPosition()` along `GetPointerDirection()`, plus a second ray along the camera's forward direction. It casts the cursor ray once and caches the hit. It tries a Bullet physics ray first and falls back to an RV-geometry raycast (`RaycastRVProxy` with `NEARESTCONTACT`, sorted), because Bullet sees only objects with physics bodies ([Editor.c](https://github.com/InclementDab/DayZ-Editor/blob/legacy/DayZEditor/Scripts/4_World/DayZEditor/classes/Editor.c)). The hit object is looked up in a static map from `Object` to editor object. A click on a known object selects it. Ctrl toggles it, Shift adds to the selection, and a click on empty space clears the selection. Ctrl+click on a map object puts a placeable copy of it "in hand", and Ctrl+middle-click deletes a placed object or hides a map object. Vanilla's own developer scene editor picks objects the same way, with `GetPointerDirection()` and `DayZPhysics.RaycastRV` ([pluginscenemanager.c](https://github.com/BohemiaInteractive/DayZ-Script-Diff/blob/main/scripts/4_world/plugins/pluginbase/pluginscenemanager.c)). COT adds a robustness trick worth adopting: it fires Fire, View and optionally Geom LOD intersection types and keeps the nearest hit, because many models lack one of those LODs ([COT JMObjectSpawnerModule.c](https://github.com/Jacob-Mango/DayZ-CommunityOnlineTools/blob/production/JM/COT/Scripts/5_Mission/CommunityOnlineTools/modules/Object/JMObjectSpawnerModule.c)). The 1.30 signatures for `RaycastRV`, `RaycastRVProxy` and the `ObjIntersect*` enum are in [dayzphysics.c](https://github.com/BohemiaInteractive/DayZ-Script-Diff/blob/main/scripts/3_game/global/dayzphysics.c).

### Box, ellipse and lasso select never touch 3D

Marquee selection is entirely 2D. Every placed object has a screen marker that is repositioned each frame with `GetGame().GetScreenPos()` and hidden when `z < 0` (the point is behind the camera) or when it is beyond the marker view distance. On mouse-up the HUD tests each marker's screen position against the rectangle, against the ellipse (`dx²/a² + dy²/b² ≤ 1`), or against the lasso polygon (a point-in-polygon test on mouse samples more than 4 px apart). A **0.12 s delay** stops ordinary clicks from starting a box, and Shift keeps the existing selection ([EditorHud.c](https://github.com/InclementDab/DayZ-Editor/blob/legacy/DayZEditor/Scripts/4_World/DayZEditor/gui/EditorHud.c); [EditorObjectWorldMarker.c](https://github.com/InclementDab/DayZ-Editor/blob/legacy/DayZEditor/Scripts/4_World/DayZEditor/gui/Markers/EditorObjectWorldMarker.c)). The rectangle itself is drawn on a `CanvasWidget`. One consequence is a limitation: an object whose marker is culled cannot be box-selected. Our version should project each candidate's bounding-box centre directly instead of relying on marker widgets. COT's ESP shows the same projection and on-screen test ([COT JMESPWidgetHandler.c](https://github.com/Jacob-Mango/DayZ-CommunityOnlineTools/blob/production/JM/COT/Scripts/5_Mission/CommunityOnlineTools/modules/ESP/JMESPWidgetHandler.c)).

### The gizmo is a scaled entity, and its handles are picked with box tests

The translate, rotate and scale gizmos are custom p3d models. One cached local entity exists per mesh. Handle colours come from procedural textures set on hidden selections (yellow on hover, orange while active). The gizmo is scaled each frame by **distance × FOV × 0.1** so it stays the same size on screen ([GizmoBase.c](https://github.com/InclementDab/DayZ-Editor/blob/legacy/DayZEditor/Scripts/4_World/DayZEditor/objects/GizmoBase.c)). Handles are never raycast against geometry. Each handle is an invisible oriented box in gizmo-local space: axis handles are 2.0 long and 0.125 wide, the centre handle is a ±0.1875 cube, and the rotation rings are thin 4.0-wide slabs. The cursor ray is tested against every box with the standard slab method, and the nearest hit wins.

Dragging is plane intersection. To drag along an axis, the editor builds the plane that contains the axis and faces the camera as squarely as possible. Its normal is `axis × (cameraForward × axis)`, which keeps the drag stable from any viewing angle. The editor intersects the cursor ray with that plane, converts the hit into the object's local frame, subtracts the grab offset stored at mouse-down (so the object does not jump), zeroes the two off-axis components and converts back to world space ([EditorTranslationGizmo.c](https://github.com/InclementDab/DayZ-Editor/blob/legacy/DayZEditor/Scripts/4_World/DayZEditor/objects/EditorTranslationGizmo.c)). Plane handles zero only the third axis, and the centre handle moves in the camera-facing plane. Holding Shift snaps to **0.4 m**, and Grid mode snaps to 1 m. Rotation intersects the ray with the ring's plane and rebuilds an orthonormal basis that points toward the hit. This rotation is *absolute*: the object's forward axis snaps to the cursor. A relative-offset variable exists in the code but its use is commented out, and there is **no angle snapping** ([EditorRotationGizmo.c](https://github.com/InclementDab/DayZ-Editor/blob/legacy/DayZEditor/Scripts/4_World/DayZEditor/objects/EditorRotationGizmo.c)). We should do better here by storing the angle at grab time, applying only the delta, and snapping to 15° with Shift.

Multi-object edits stay rigid because, at drag start, every non-primary selected object stores its transform relative to the primary object, and is rebuilt from that relative transform every frame. Keyboard nudging (arrows, PgUp/PgDn) works in world-flat, camera-flat or camera-3D frames around the selection's average position. Shift and Alt scale the step by about 6.7, and one press-through-release becomes one undo entry ([Editor.c](https://github.com/InclementDab/DayZ-Editor/blob/legacy/DayZEditor/Scripts/4_World/DayZEditor/classes/Editor.c)).

### Placement puts the object's bottom, not its origin, on the hit point

While placing, the editor holds a "hologram". This is a real local object created with `ECE_LOCAL` (or `CreateStaticObjectUsingP3D` for raw p3d paths) with simulation disabled ([EditorWorldObject.c](https://github.com/InclementDab/DayZ-Editor/blob/legacy/DayZEditor/Scripts/4_World/DayZEditor/classes/EditorWorldObject.c)). Each frame it is moved to the cursor raycast hit, which ignores the player and the hologram itself. Its transform is then offset upward by the negative of the clipping box's minimum Y, so the object's lowest point rests on the surface whatever its model origin. Magnet mode uses the hit normal as the up axis. R adds 90° of yaw, the optics-zoom inputs rotate in 9° steps, and Shift keeps the hologram in hand for repeated placement ([Editor.c](https://github.com/InclementDab/DayZ-Editor/blob/legacy/DayZEditor/Scripts/4_World/DayZEditor/classes/Editor.c)). The bounding box for the selection highlight comes from `ClippingInfo`. It is drawn once with `Shape.CreateLines` and moved each frame with `SetMatrix` ([EditorObject.c](https://github.com/InclementDab/DayZ-Editor/blob/legacy/DayZEditor/Scripts/4_World/DayZEditor/classes/EditorObject.c)). Vanilla offers equivalent building blocks for slope alignment. The base-building hologram combines the user's yaw with angles derived from the surface normal, and `Math3D.DirectionAndUpMatrix` builds a basis directly from a forward vector and a normal ([hologram.c](https://github.com/BohemiaInteractive/DayZ-Script-Diff/blob/main/scripts/4_world/classes/hologram.c); [enmath3d.c](https://github.com/BohemiaInteractive/DayZ-Script-Diff/blob/main/scripts/1_core/proto/enmath3d.c)).

## Undo, clipboard, camera and catalogue are simple, with known weaknesses

Undo is a linear array of action objects. Each stores an undo method name, a redo method name and lists of `Param` arguments, and replay calls the methods by name through `g_Script.Call`. Objects are referenced by integer session ID, and a session cache keeps each object's data alive so that undoing a delete can recreate it. Inserting a new action drops the redo branch. The stack is **unbounded**: a 512-entry stack class exists but is unused ([EditorAction.c](https://github.com/InclementDab/DayZ-Editor/blob/legacy/DayZEditor/Scripts/4_World/DayZEditor/classes/EditorAction.c)). Calling methods by name fails silently when a name is misspelt or a `Param` has the wrong type. A typed command class with `Do()`/`Undo()` methods, keyed by a stable editor GUID instead of an `Object` reference, is safer. It is also needed for buildings, because recreating a building invalidates any references to it.

Copy serialises the selected objects' data to JSON on the OS clipboard with `GetGame().CopyToClipboard`. Paste re-centres the pasted group on the cursor, and Duplicate (Ctrl+J) recreates the objects in place and selects the copies so the gizmo can drag them away immediately ([EditorClipboard.c](https://github.com/InclementDab/DayZ-Editor/blob/legacy/DayZEditor/Scripts/4_World/DayZEditor/classes/EditorClipboard.c); [EditorDuplicateCommand.c](https://github.com/InclementDab/DayZ-Editor/blob/legacy/DayZEditor/Scripts/4_World/DayZEditor/classes/Commands/Clipboard/EditorDuplicateCommand.c)). Because the clipboard holds plain JSON, objects can be moved between sessions and tools, and our editor should keep that property.

The camera is a scripted `Camera` with its own `EOnFrame`. It flies on linear and angular velocities driven by the vanilla move inputs, with a **default speed of 60 m/s (range 1–300)**. Shift multiplies speed by 6.25 and Alt divides it by 6.25, and the mouse wheel changes speed by 10% per tick. Mouse-look only happens while the right mouse button is held or the cursor is hidden. Pitch is clamped to ±87°, FOV defaults to 75° and zooms smoothly, and an optional sphere-cast stops the camera at geometry. Middle-click glides to the cursor point while keeping the current height above ground. Holding Ctrl locks movement so that WASD does not move the camera during shortcuts ([EditorCamera.c](https://github.com/InclementDab/DayZ-Editor/blob/legacy/DayZEditor/Scripts/4_World/DayZEditor/classes/EditorCamera.c)).

The catalogue is built at startup by walking `CfgVehicles`, `CfgWeapons` and `CfgMagazines`. It skips classes with scope 0 and a forbidden list of classes known to crash or spam errors (`Fx` types, test-bed weapons and others). It also adds a static-p3d variant of each class's model, and enumerates plant and rock p3ds with a DF directory helper. The browser tree is built purely from the model path, so `dz/structures/...` becomes the folder hierarchy without any hand-maintained categories. Search is a substring filter that applies once more than two characters are typed, and parent folders reveal themselves when a child matches ([EditorObjectManager.c](https://github.com/InclementDab/DayZ-Editor/blob/legacy/DayZEditor/Scripts/4_World/DayZEditor/modules/EditorObjectManager.c); [EditorHud.c](https://github.com/InclementDab/DayZ-Editor/blob/legacy/DayZEditor/Scripts/4_World/DayZEditor/gui/EditorHud.c)). Previews use `ItemPreviewWidget`.

Hotkeys come from two systems. Commands declare their key combinations, which are stored as an order-independent bitmask of held keys. Continuous actions are UA inputs defined in `Inputs.xml` ([EditorCommandManager.c](https://github.com/InclementDab/DayZ-Editor/blob/legacy/DayZEditor/Scripts/4_World/DayZEditor/classes/Commands/EditorCommandManager.c); [Inputs.xml](https://github.com/InclementDab/DayZ-Editor/blob/legacy/DayZEditor/Scripts/Data/Inputs.xml)). The bitmask has real clashes: **P is both Lasso and Copy Position, and Ctrl+4 is both Grid and Collision**. The table lists the bindings that users will expect us to honour.

| Area | Bindings in the current code |
|---|---|
| File | Ctrl+N new, Ctrl+O open, Ctrl+S save, Ctrl+Shift+S save as |

## The .dze format is binary FileSerializer data with a JSON fallback

The save classes live in Dabs Framework, not in the editor. The current editor always writes **binary**: an Enforce `FileSerializer` stream that starts with the string `"EditorBinned"` followed by **version 8**. Readers check that first string and fall back to JSON if it is missing, because older editors wrote JSON ([EditorSaveData.c](https://github.com/InclementDab/DayZ-Dabs-Framework/blob/production/DabsFramework/Scripts/3_Game/DabsFramework/_Legacy/Editor/EditorSaveData.c)). The top level contains `MapName`, `CameraPosition`, `AuthorId`/`CreditIds` and Unix-epoch `LastModified`/`CreationDate` (version 7 and later), then the `EditorObjects`, `EditorHiddenObjects` and `CameraTracks` arrays. The author's C# reader documents the primitive encoding. An int is 4 bytes little-endian. A bool is stored as a 4-byte int. A string is an int32 length followed by the bytes. A vector is a count (always 3) followed by three floats ([EnfusionSerializer.cs](https://github.com/InclementDab/DayZ-Editor/blob/legacy/BinEditor/Enfusion-Deserializer/DayZ-Bin-Editor/Enfusion/EnfusionSerializer.cs)).

A placed object carries `Type`, `DisplayName`, `Position` (absolute world coordinates), `Orientation` (yaw, pitch, roll in degrees), `Scale`, a `Flags` bitmask, typed `Parameters`, four bools (`EditorOnly`, `Locked`, `AllowDamage`, `Simulate`), `Model`, and in version 8 a recursive `AttachmentMap` ([EditorObjectData.c](https://github.com/InclementDab/DayZ-Dabs-Framework/blob/production/DabsFramework/Scripts/3_Game/DabsFramework/_Legacy/Editor/EditorObjectData.c)). One convention trap matters for importers. **For raw `.p3d` entries the file stores the model-origin position (world position minus the bounding centre) and the orientation in radians**, while class-name entries store world position and degrees ([EditorDZEFile.c](https://github.com/InclementDab/DayZ-Editor/blob/legacy/DayZEditor/Scripts/4_World/DayZEditor/classes/FileManagers/FileTypes/EditorDZEFile.c)). A hidden map object has **no ID**. It is a deprecated `Type`, a `ModelName` (shape name) and a `Position`, and it is re-found by searching a **0.1 m** radius and matching the lower-cased shape name, falling back to the type ([EditorDeletedObjectData.c](https://github.com/InclementDab/DayZ-Dabs-Framework/blob/production/DabsFramework/Scripts/3_Game/DabsFramework/_Legacy/Editor/EditorDeletedObjectData.c)). The read path branches on version: v2 added attachments and parameters, v3 the bools, v5 `Model`, v6 `ModelName`, camera tracks start after v5, v7 added the author block, and v8 the `AttachmentMap`. **Deletion records in v6 and v7 files have no `Type` field**, and a reader that expects one misaligns the whole stream. The JSON key for deletions changed from `EditorDeletedObjects` to `EditorHiddenObjects` during 2024 ([DF at 7469248](https://github.com/InclementDab/DayZ-Dabs-Framework/blob/7469248406/DabsFramework/Scripts/3_Game/DabsFramework/_Legacy/Editor/EditorSaveData.c)). Because Enforce JSON maps fields by name, older JSON files' deletions are probably being silently ignored by current loaders. This is an inference, not a tested result. Real-world JSON files often omit `Version` and use `Flags: 2147483647` ([codelocks.dze](https://github.com/DayZNETWORk/EditorFiles/blob/main/codelocks.dze)).

The Export menu writes eight formats, listed in the table ([EditorExportMenu.c](https://github.com/InclementDab/DayZ-Editor/blob/legacy/DayZEditor/Scripts/4_World/DayZEditor/gui/Menus/Menus/EditorExportMenu.c)). **Only `.dze` and Expansion `.map` carry deletions.** Export settings for relative height and offset exist but no exporter reads them ([ExportSettings.c](https://github.com/InclementDab/DayZ-Editor/blob/legacy/DayZEditor/Scripts/3_Game/DayZEditor/classes/ExportSettings.c)).

## The Loader spawns at mission start and hides map statics on every client

The current Loader is one file. In `OnMissionStart()`, after `super` (so after init.c and CE/Hive initialisation), it creates `$mission:\EditorFiles`, recursively enumerates `*.dze` files to depth 5, and reads each one as binary or JSON. It then processes **deletions first, creations second**. Class names spawn with `CreateObjectEx(type, pos, ECE_SETUP | ECE_UPDATEPATHGRAPH | ECE_CREATEPHYSICS)` followed by `SetOrientation` and `SetScale`. Raw `.p3d` paths go through `CreateStaticObjectUsingP3D`. `EditorOnly` entries are skipped, `DisableSimulation` is applied when `Simulate` is false, and a single `ProcessMarkedObjectsForPathgraphUpdate()` runs at the end ([Loader MissionServer.c](https://github.com/InclementDab/DayZ-Editor-Loader/blob/main/EditorLoader/Scripts/5_Mission/EditorLoader/Mission/MissionServer.c)). The objects are ordinary networked entities and are never written to storage, so the `.dze` file is the source of truth and the objects are recreated on every boot. The 2023 version also passed `ECE_NOLIFETIME | ECE_DYNAMIC_PERSISTENCY`. The current one does not, which in principle exposes item-type objects to CE lifetime cleanup. This is inferred from the flags and has not been tested ([2023 MissionServer.c](https://raw.githubusercontent.com/InclementDab/DayZ-Editor-Loader/64a7226c/DayZEditorLoader/Scripts/5_Mission/DayZEditorLoader/Mission/MissionServer.c)). An empty `LoadCustomBuilds` hook lets other mods append files, and since August 2025 the Loader rewrites `mapgrouppos.xml` after spawning, skipping suppressed objects. Loot positions therefore need a second restart, because CE has already read that file by the time the Loader rewrites it.

Hiding is the part that needs care. Map objects are baked into the world file that every client loads locally, so they have no network identity, and a server-side change alone does not reach clients. The Loader re-finds each record by position and shape name and calls DF's `Suppress`. That sets the scale to 0.000001, clears the object's flags and event mask, sets `NOTVISIBLE`, destroys the physics body with `dBodyDestroy`, and updates the pathgraph region. The server then broadcasts an RPC carrying the object references, and re-sends the whole list to each connecting player ([DF SuppressedObject.c](https://github.com/InclementDab/DayZ-Dabs-Framework/blob/production/DabsFramework/Scripts/3_Game/DabsFramework/Suppression/SuppressedObject.c); [DF SupressedObjectManager.c](https://github.com/InclementDab/DayZ-Dabs-Framework/blob/production/DabsFramework/Scripts/3_Game/DabsFramework/Suppression/SupressedObjectManager.c)). The author's comments in that code record which alternatives failed: **scale 0 "will absolutely destroy the heap", a tiny scale leaves collision unless the body is destroyed, and SetPosition/SetTransform "leaves a client ghost"**. Restoring does not bring physics back ("un-deleted objects dont get their physics back"). Expansion takes the opposite approach. It moves the object 1000 m down, calls `dBodySetSolid(obj, false)`, marks the pathgraph, and sends a type-hash-plus-position list to each connecting client, which applies the same change locally. Its destructor restores everything, so the hide is reversible ([ExpansionWorldObjectsModule.c](https://github.com/salutesh/DayZ-Expansion-Scripts/blob/experimental/DayZExpansion/Core/Scripts/4_World/DayZExpansion_Core/ExpansionWorldObjectsModule.c)). The two mods disagree about moving the object (DF warns of ghosts, Expansion ships it), and neither avoids `ObjectDelete` because of a documented engine rule; they simply avoid it. We have to settle this with our own test.

The Loader's history shows where this goes wrong. Linux failed to find `.dze` files until October 2024 ([issue #4](https://github.com/InclementDab/DayZ-Editor-Loader/issues/4)). Exported loot positions included deleted buildings ([issue #6](https://github.com/InclementDab/DayZ-Editor-Loader/issues/6)). The changelog records bullets and 40mm grenades sticking in builds, an exploit that let cheaters remove buildings (Feb 2022), a "re-delete builds once" format change, and an August 2025 reversion followed by a "crash on launch with invalid objects" fix ([Workshop changelog](https://steamcommunity.com/sharedfiles/filedetails/changelog/2276010135); [changelog p2](https://steamcommunity.com/sharedfiles/filedetails/changelog/2276010135?p=2)). The structural weakness is that matching on position within 0.1 m plus model name fails *silently* when a map update moves or renames an object, because the "not found" log line is commented out. Our hide records should log every miss and appear in an admin report.

## CC BY-NC-ND licensing rules out every copy-paste shortcut

Static buildings are the first verification item. The RV engine's long-standing rule is that statics with the "house" simulation type do not sync position changes over the network ([BI wiki setPos](https://community.bistudio.com/wiki/setPos)). BI tickets report that `SetScale` and `SetPosition` on script-spawned structures desync collision from visuals ([T156159](https://feedback.bistudio.com/T156159); [T134421](https://feedback.bistudio.com/T134421)). Vanilla's own Object Spawner sidesteps the problem by setting orientation and scale immediately after creation, before any client connects. When a House-type object changes during a live session, the server should either delete and recreate it at the new transform, or call `RemoteObjectTreeDelete` + `RemoteObjectTreeCreate` so that clients re-instantiate it, which is what COT does after local setup ([COT JMObjectSpawnerModule.c](https://github.com/Jacob-Mango/DayZ-CommunityOnlineTools/blob/production/JM/COT/Scripts/5_Mission/CommunityOnlineTools/modules/Object/JMObjectSpawnerModule.c)). Recreating the object is the safer default, because our GUID-keyed undo already tolerates replaced `Object` references.

Map-object removal is the second item. Three candidates need a two-client test (one client joining before the change and one after), each checked for visibility, collision on foot, bullet passage, AI pathing and restore. The first is `ObjectDelete` on the server plus the client copy. The second is a scale/flags/`NOTVISIBLE`/`dBodyDestroy` hide. The third is a move-down plus `dBodySetSolid(false)` hide. Undo needs reversibility, which favours the move-down approach, but only if the "client ghost" DF warns about does not appear when every client applies the move itself. Live hides should also be persisted, so the authoritative restore path is a server restart and live un-hide is best-effort. The third item, `Shape` rendering in the retail executable, matters because retail Workshop mods (the Editor, COT, Expansion) draw with it and the API is declared outside `#ifdef DIAG`. That is indirect evidence only. The canvas fallback keeps the editor usable either way. Smaller unknowns are the meaning of `CreateStaticObjectUsingP3D`'s `createLocal` argument for networked statics ([game.c](https://github.com/BohemiaInteractive/DayZ-Script-Diff/blob/main/scripts/3_game/global/game.c)), the semantics of `GetWorldDirectionFromScreen`, and the size limit on a large connect-time hide-list RPC. We should send hide records (type + position) in chunks, rather than `Object` references, because records can be resolved independently on each machine.

## A five-phase plan that verifies the risky parts first

The editor set should be our own JSON, versioned from day one and saved per map. A sensible layout is `$profile:DRP_Admin/EditorSets/<world>/<set>.json`, holding a `Version`, the set `Name`, `Enabled`, an `Objects` array (`Id` GUID, `Type`, `Pos`, `Ypr` in degrees, `Scale`, `Flags`, `Simulate`) and a `Hidden` array (`Type`, `Shape`, `Pos`). The server is the only writer: clients request edits by RPC, and the server checks the admin permission, applies the edit, writes the file atomically and broadcasts the result. Keep the vanilla Object Spawner's field meanings (degrees, world positions, `ypr`) so that converting to and from `cfggameplay` JSON is lossless.

| Phase | Deliverable | Exit criterion (in game) |
|---|---|---|
| 0. Spikes | Three throwaway tests: Shape lines in retail client; move a spawned `Land_` building live with recreate vs `RemoteObjectTree*`; hide a map house by each of the three methods with a JIP second client | Pick the drawing path, the building-move rule and the hide method; record results in memory notes |
| 1. Server pipeline | Set schema + loader in `MissionServer.OnMissionStart` (spawn flags as vanilla spawner, batched pathgraph), hide records applied on server and sent chunked to clients on connect and on change; miss logging; admin commands to list/enable sets | Restart twice with no duplicates; late-joining client sees hides; every miss logged |
| 2. Core editing | Free camera (velocity fly, RMB look, wheel speed, Ctrl locks move); cursor pick; click/Shift/Ctrl selection; bounding boxes; marquee box select; Delete/hide; typed undo/redo; JSON clipboard copy/paste/duplicate; commit-on-release RPCs | Ten-object edit session survives undo/redo to start and a restart reproduces the final state |
| 3. Gizmo and placement | Translate (axis, plane, free), relative rotate with 15° snap, uniform scale; bottom-on-surface placement with magnet/ground modes; keyboard nudge; multi-select rigid moves via stored relative matrices | Placed objects sit flush on slopes and roofs; multi-select rotate keeps formation |

Browser and polish | Catalogue from `CfgVehicles` scope ≥1 with a crash blacklist plus a tool-generated p3d list for plants/rocks (no runtime directory enumeration inside PBOs); model-path tree; search >2 chars; favourites; `ItemPreviewWidget`; command registry that drives menus and hotkeys, with no key clashes | Browse-place-save loop without leaving the game |
| 5. Interop | Import JSON `.dze` (accept both deletion keys, missing `Version`, p3d radians/origin convention), Expansion `.map`, vanilla spawner JSON; export spawner JSON, `.map`, mapgrouppos with hidden houses excluded; optional binary `.dze` reader written from the field order alone | Round-trip a community `.dze` with deletions onto a test map |

Two design choices deserve emphasis. First, the command registry is the one architectural idea worth adopting wholesale: a single object owns a command's name, icon, shortcut, `CanExecute` and `Execute`, so menus, toolbar and hotkeys share one registration. We would write our own version, keyed on modifier-plus-key rather than an order-free bitmask, so the P and Ctrl+4 clashes cannot happen. Second, Phase 0 decides whether Phases 2–3 draw with `Shape` or with a canvas, and whether building moves recreate objects. Running it first stops two potentially expensive rewrites. Per the shared test-server protocol, every spike and phase test should use the shared DRP test server and confirm that all `@DRP_Core` mods still load.

## Conclusion

The DayZ Editor's quality comes less from clever engineering than from a few correct geometric choices: a camera-facing drag plane, offsets stored at grab time, bottom-pivot placement and projected-point marquee selection. These are the cheapest things to rebuild, and our tool can improve on them with relative rotation, angle snapping and selection that does not depend on visible markers. The expensive and fragile parts are where the Editor and Loader have struggled for five years: making map-object removal consistent across server, existing clients and late joiners, and keeping deletion records valid across map updates. DRPA_Editor gets these right by being server-authoritative from the start, by keying everything on GUIDs and logged shape-plus-position records instead of `Object` references, and by settling the three engine questions empirically in Phase 0 rather than inheriting another mod's assumptions.

The licensing finding changes the plan in a useful way. A clean-room build is mandatory, and it also yields a smaller, dependency-free editor whose save format matches the vanilla Object Spawner, so the output stays usable even without our mod. The `.dze` ecosystem then becomes an import source we read on our own terms rather than a format we have to emulate.
